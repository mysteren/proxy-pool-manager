# Стратегия тестирования

## Флаги тестирования

На этапе MVP интеграционные и E2E-тесты **выключены** — включать их будем
позже, когда приложение станет сложнее. Флаги нужны, чтобы это было явно
видно и не забылось.

| Флаг                       | Значение (MVP) | Что включает                                     |
|----------------------------|----------------|--------------------------------------------------|
| `INTEGRATION_TESTS_ENABLED`| `false`        | Сценарные тесты через реальный бэкенд           |
| `E2E_TESTS_ENABLED`        | `false`        | E2E через Wails server mode (см. ниже)          |

Пока флаги имеют смысл только в документации и в чек-листах релиза:
автоматических интеграционных/E2E-тестов в репозитории нет. Когда включим —
эти флаги станут настройками запуска тестов.

## Проверка прокси

Критерий «рабочий» — **не только открытый порт**, а реальный обмен трафиком
через прокси. Это важнее скорости: лучше меньше прокси, но честных.

### Latency

**Метод:** TCP-connect к `host:port`.

- `net.Dialer.DialContext(ctx, "tcp", addr)` с таймаутом
  (`settings.latency_timeout_ms`, по умолчанию 5 секунд).
- Используется именно `DialContext` (а не `net.DialTimeout`), чтобы
  отмена массового теста прерывала уже висящие подключения.
- Замер: время от вызова до успешного `connect` → `latency_ms`.

### Подтверждение работоспособности (HTTP)

TCP-connect может «пройти» для не-прокси сервиса. Поэтому после успешного
connect выполняется **лёгкий HTTP-запрос через сам прокси**.

- URL по умолчанию: `https://api.ipify.org?format=json`
  (`settings.http_validation_url`), таймаут — `latency_timeout_ms`.
- Транспорт:
  - `http` — `http.Transport{Proxy: http.ProxyURL(...)}`;
  - `socks5` — `golang.org/x/net/proxy.SOCKS5` + `DialContext`.
- Запрос идёт на **HTTPS**-цель, чтобы проверить в том числе туннель CONNECT.
- Успешный ответ → `is_working = true`, `latency_ms` = время TCP-connect.
- Ошибка/Tаймаут → `is_working = false`, `latency_ms = nil`.
- Отключается настройкой `validate_via_http = false` (тогда критерий —
  только TCP-connect, но это считается менее надёжным).

### Скорость (download)

Запускается **только для прокси, прошедших проверку работоспособности**.

- URL: `https://speed.cloudflare.com/__down?bytes=N`
  (`settings.speed_download_bytes`, 100 КБ – 10 МБ).
- Замер: `bytes / elapsed_seconds`, в Mbps; таймаут 30 секунд.
- Ошибка → `download_mbps = nil`.

### Конкурентность

- Число одновременных проверок — **настройка** `test_concurrency`
  (по умолчанию 50). Пользователь может снизить её, чтобы уменьшить
  нагрузку на сеть/DNS.
- Реализация: `golang.org/x/sync/semaphore` или пул воркеров.
- Скорость (download) — отдельный, меньший лимит (по умолчанию 10).

### Отмена

- `context.WithCancel` на каждый массовый тест; `cancel` хранится
  в `TesterService` под мьютексом (доступ из разных горутин).
- В цикле проверяется `ctx.Err()`; `DialContext`/HTTP-запросы принимают `ctx`.
- При отмене — событие `test:completed{cancelled: true}`.

### Повторная проверка

- Выбранные — по кнопке/хоткею.
- Все нерабочие — отдельной кнопкой.
- Все в пуле — с подтверждением (может быть долго).

### Протоколы

- Проверяются `http` и `socks5`.
- `https` нормализуется в `http` при парсинге.
- `socks4` не поддерживается (Go `x/net/proxy` умеет только SOCKS5).

## Тестирование приложения

### Go (backend)

- **Unit-тесты:**
  - `parser_test.go` — `ip:port`, `protocol://ip:port`, JSON, нормализация `https`.
  - `storage_test.go` — CRUD, дедупликация по `host+port+protocol`,
    фильтрация, пагинация, экспорт.
  - `tester_test.go` — проверка работоспособности через `httptest`
    (мок-прокси и мок-цель).
- **Инструменты:** стандартный `testing`, `github.com/stretchr/testify`.
- **Команда:** `go test ./...`

### Frontend

- **Unit-тесты:**
  - Компоненты таблицы: рендер, сортировка, пагинация, выбор.
  - Утилиты: форматирование latency, относительное время (`Intl`).
- **Инструменты:** `vitest`, `@testing-library/react`, `@testing-library/jest-dom`.
- **Команда:** `npm run test` (в `frontend/`).
- ⚠️ Инфраструктура тестов фронтенда ещё не настроена — заведём, когда
  появятся первые компоненты (Milestone 1/3).

### Интеграционные и E2E

⛔ **Отключено на MVP** (`INTEGRATION_TESTS_ENABLED = false`,
`E2E_TESTS_ENABLED = false`).

Когда включим:

- **Интеграционные сценарии** (реальный бэкенд):
  1. Добавить источник URL → прокси попали в БД.
  2. Запустить проверку → статус обновился честно.
  3. Отфильтровать только рабочие → корректно.
  4. Скопировать выбранные → буфер обмена.
- **E2E:** через режим Wails `build:server` / `run:server` — бэкенд и
  биндинги отдаются по HTTP без нативного окна, и тест-раннер работает
  с настоящим приложением. Это дешевле и надёжнее, чем Playwright + WebView.
  Нативные вещи (диалоги, буфер, системная тема) server mode не покрывает —
  они остаются в ручном чек-листе.

### Ручное тестирование

- **Чек-лист релиза:**
  - [ ] Сборка `wails3 build` проходит без ошибок.
  - [ ] Приложение запускается на чистой системе (Linux GNOME и KDE).
  - [ ] Тёмная и светлая темы корректно переключаются.
  - [ ] Проверка нерабочих прокси честно помечает их нерабочими.
  - [ ] Число одновременных проверок меняется в Настройках и влияет на нагрузку.
  - [ ] Отмена теста не оставляет висящих горутин.
  - [ ] Копирование в буфер работает в GNOME и KDE (через Go `app.Clipboard`).
  - [ ] Экспорт в TXT/CSV/JSON корректен.
  - [ ] SQLite-файл создаётся в правильной директории (`xdg.DataHome()`).

## Метрики качества

- Покрытие Go-кода тестами: ≥ 60% на момент Milestone 4.
- Покрытие Frontend: ≥ 40% на момент Milestone 4.
- Отсутствие `go vet` и `eslint` предупреждений.
